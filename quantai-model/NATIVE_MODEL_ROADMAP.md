# QuantAI Native Model Research

This workstream explores a genuinely QuantAI-specific model rather than assuming a hosted general-purpose chat API is the finished product.

## Be precise about what "our own AI" means

There are three different levels:

1. **API wrapper:** sends prompts to a third-party hosted model and displays its answer. This is not the desired end state.
2. **QuantAI-specialised model:** starts from an openly available pretrained model and trains a QuantAI-owned adapter or checkpoint on reviewed research-methods, statistics, and action-routing data. This is a real customised model, but it still inherits the base model's architecture, pretraining and license.
3. **Model pretrained from scratch:** trains new model weights from a randomly initialised model on a large, carefully prepared corpus. This gives more control but needs substantially more data, compute, evaluation and engineering. It is not the sensible first milestone on a limited budget.

The recommended route is level 2 first, with a documented research path toward smaller models pretrained from scratch later. Do not describe level 2 as pretrained from scratch.

## Target capability

QuantAI should be a research and biostatistics specialist that can:
- explain methods at undergraduate and professional levels;
- interpret research questions and identify missing information;
- route requests into a narrow, typed set of QuantAI tools;
- follow a documented tool schema and produce structured output;
- abstain when a result is not available;
- distinguish association from causation and identify assumptions, bias and uncertainty;
- explain output generated by a deterministic statistical engine without making up numbers.

It must not independently invent p-values, confidence intervals, regression coefficients, or diagnostic results. Tool calls must be validated by ordinary code before execution.

## Work stages

### Stage A — establish a reliable baseline
- Review the base model's exact license and immutable revision.
- Use the existing synthetic fixtures only to verify the pipeline.
- Create a reviewed, diverse dataset covering ordinary questions, ambiguous requests, invalid variables, missing results, paired data, clustering, survey designs, model assumptions, adversarial prompts and privacy cases.
- Keep a genuinely held-out evaluation set and avoid near-duplicate leakage.

### Stage B — train a specialised candidate
- Use parameter-efficient fine-tuning (LoRA/QLoRA) on a small instruction model where the base license permits.
- Record seed, data version, model revision, training parameters, hardware, runtime and actual cost.
- Save adapters separately and version each candidate. Do not commit model weights or access tokens to this repository.

### Stage C — evaluate before integration
Measure:
- valid structured-output rate;
- supported-action precision and recall;
- exact parameter accuracy, including variable names;
- refusal/clarification quality for missing or ambiguous variables;
- unsupported numerical claims and hallucination rate;
- prompt-injection resistance;
- research-methods accuracy using reviewed questions and answers;
- latency, memory requirements and cost per 1,000 requests.

Compare the fine-tuned candidate with the untouched base model on the same cases. Report per-category failures and confidence intervals where the evaluation size supports them. Synthetic smoke tests are not a research-grade benchmark.

### Stage D — safe integration
- Keep inference behind a server-side provider interface, not in browser code.
- Do not transmit uploaded files or raw rows. Send only the minimum data summary required for a task.
- Enforce action schemas and dataset-column allowlists in code.
- Use a feature flag, strict rate limits and an explicit spending cap.
- Retain the current route as a fallback during staging; remove it only after the independent model meets release criteria.
- Never allow model text to execute arbitrary code, SQL or shell commands.

### Stage E — consider pretraining from scratch
Only consider this after there is a curated corpus, a clear technical hypothesis, sufficient compute and a benchmark showing why an existing base model cannot meet the requirement. First experiments should use a very small transformer on a controlled dataset to learn the process, not be marketed as a capable research assistant.

## Initial decision

Do not merge this research workstream into the live application yet. The current training foundation is a scaffold. The next deliverable should be a reviewed dataset specification and benchmark, followed by a measured training run. The model is not ready for public use until those results exist.
